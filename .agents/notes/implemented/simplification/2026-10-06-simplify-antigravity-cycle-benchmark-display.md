# Agent Note: 简化并修正 Antigravity 算力池周期测定用量算法与界面展示

Status: implemented

## Problem
在前端 Antigravity 算力池卡片中，展示多账号用量基准的模块原称为“加权用量统计”，且文案标注“基于就绪账号会话余量加权聚合”，该命名造成了严重概念误导：
1. 实际上并没有做加权平均，而是多账号在各周期内的真实消耗/容量测算；
2. 算法中存在硬编码推算：月度用量在缺少归档时直接通过 `liveAvgWeekly * 4.33` 凭空放大，并非真实测得的自然月用量；
3. 计算实时在册平均时，未打满的未完成窗口（当前切片已跑 Token）被当做完整周期的基准样本强行平均，拉低了真实的“单账号完整周期额度/容量”基准；
4. 面向普通用户过于晦涩且充满不真实的推算数字，违背了“通过持续真实使用多账号多周期测量真实用量”的初衷。

## Decision
1. **界面与语义精简**：
   - 将“加权用量统计”更名为“周期基准用量”；
   - 副文案精简为“多账号真实测定的单账号周期用量基准”；
   - 容量水位说明精简为“基于当前就绪账号剩余额度”；
2. **算法真实性修正**：
   - 彻底废除 `* 4.33` 硬编码倍率推算，月度用量必须基于真实持久化归档（`benchmark.kind_monthly`）或真实的月度统计窗口，若无样本则显示为 `--`；
   - 周期容量基准计算中，仅将“已打满归档（`completed_5h_stats`）”与“斜率推测的打满容量（`estimated_capacity`）”作为完整周期样本；未打满的实时窗口不计入完整周期平均分子与分母中；
   - 优先使用后端通过全局持久化快照沉淀的跨账号跨周期真实基准 `props.benchmark`，越用越准确。

## Alternatives considered
- **保留“加权”概念并引入打满置信度加权模型**：
  增加了复杂的加权系数计算（如按请求次数、打满时间窗口赋权），算法变黑盒且用户无法理解，不如直接以实测均值呈现。
- **保留月度 4.33x 推算**：
  在系统刚启动无月度数据时能显示出数字，但该数字为伪数据，容易误导用户对月度额度上限的判断。显示 `--` 直观反映真实测量进度更为诚信与严谨。
