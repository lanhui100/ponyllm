# Agent Note: 遥测时序聚合与连通性探测采样架构设计

Status: implemented

## Problem

当前 PonyLLM 遥测体系在支撑现代前端 Dashboard 深度可观测时存在两项关键能力缺失：
1. **历史多周期时序聚合缺失**：当前 `MetricsCollector` 仅在内存中维护全局单调递增计数器，所有时序曲线依赖前端本地内存短周期 delta 计算。当大盘需要查看 24小时 / 7天 / 30天 周期指标，以及需要按 Provider 和 Model 细分统计 Token 吞吐时，后端缺乏时间桶（Time Bucket）滑动聚合与对外查询接口。
2. **微时隙连通性采样缺失**：当前 Provider 与网关健康度仅有布尔状态或全局平均 TTFT，缺乏最近 1 分钟（40 根时隙柱）高密度的连通性心跳与延迟探测序列，无法向前端供给 40 根连通性状态条（Uptime Bars）所需的数据。

## Decision

在 `ponyllm-core` 与 `ponyllm-server` 中实现轻量级、零外部依赖的滑动时序聚合与定长环形连通性采样：

1. **定长环形连通性采样器（`ConnectivitySampler`）**：
   - 为网关自身心跳及各活跃 Provider 维护定长环形采样缓冲区（40 槽位，单槽位 1.5s 步长，严格覆盖最近 1 分钟）；
   - 单次样本更新复杂度为 $O(1)$，槽位内仅维护标量统计计数与累加值，内存恒定受控（零无界增长、零热路径线性扫描）；
   - 按阈值规则判定状态：及时（< 300ms）、一般（300ms ~ 1000ms）、超时/失败（≥ 1000ms 或 HTTP 错误）；
   - 在 `/v1/telemetry/stream` 中输出包含各 Provider（覆盖流式与非流式上游）及网关的 40 槽位连通性快照与最新一次延迟。

2. **多周期滑动时间桶投影（`TimeseriesProjection`）**：
   - 作为 `EventBus` 投影，在内存中维护 720 个自然小时桶（覆盖 30 天）：
     - **24 小时周期**：1 小时时间桶粒度（24 个 bucket，对齐自然整点）；
     - **7 天周期**：6 小时时间桶粒度（28 个 bucket，对齐 6 小时自然边界）；
     - **30 天周期**：24 小时时间桶粒度（30 个 bucket，对齐每日自然边界）；
   - 包含时钟前跳防全量抹除机制、以及所有浮点指标的 `is_finite()` 守卫；
   - 桶内按 Provider 与 Model 细分聚合 Token 吞吐与总量。

3. **对外 API 端点**：
   - 暴露 `GET /v1/telemetry/history?range=24h|7d|30d`，对 `range` 参数进行强校验，返回各周期聚合时序指标与维度切片；
   - 扩展 `/v1/telemetry/stream` 输出完整 Provider 全集与网关的 40 槽位连通性快照。

## Alternatives considered

1. **实时读取并反序列化磁盘上的 hourly JSONL 分段文件**：
   - 优点：无需额外内存维护聚合桶。
   - 缺点：随着请求量增加，I/O 开销与反序列化 CPU 消耗不可控，可能阻塞或拖慢网关响应，破坏“可观测性绝不影响热路径”的基本原则。
2. **引入外部时序数据库（Prometheus / InfluxDB / SQLite）**：
   - 优点：成熟的时序存储与查询语法。
   - 缺点：破坏 PonyLLM 作为单二进制、零重型依赖、极简部署的核心定位，极大增加部署与运维负担。
3. **完全由前端在浏览器本地缓存（LocalStorage）拼接时序**：
   - 优点：后端零改动。
   - 缺点：换浏览器或刷新后历史丢失；无法支持离线期间数据填补；多客户端视角不一致；违背“所有 UI 实现必须有后端需要的支持”的原则。

## Consequences

- 满足了现代大盘对历史趋势分析与微时隙连通性展示的数据诉求；
- 内存严格常数级可控，热路径锁竞争完全消除；
- 前端无需重型图表数据拼接逻辑，可直接消费标准时序数组。
