# Agent Note: 412 冲突自动重试与人话文案

Status: implemented

## Decision

用户添加模型时撞见的 412 弹窗，根因不是"有人抢改"：Antigravity 密钥
后台轮换会自动写盘并 bump `config_version`，页面手里的版本号一旦过期，
下一次提交即被判冲突。修复分两层（纯前端，`web/dist` 已重建，
线上网关无需重启）：

- `runWithConflictCheck` 遇到 412 先 `fetchAll` 刷新到最新并自动重试一次；
  重试仍 412 才认为是真正的并发修改并弹窗。后台轮换这类单发过期从此静默
  自愈（含批量添加循环，每次 `saveModel` 自带刷新+重试）。
- 弹窗去术语化：标题改为"网关配置刚被改过，提交没成功"，正文说明最可能的
  两个原因（后台自动续期密钥/另一个管理页面修改）并明确"已填内容还在，
  刷新后重设点一次保存即可"；按钮改为"知道了/刷新数据"。

## Alternatives considered

- 后端轮换写盘不 bump 版本：落选。文件内容确实变了，版本号必须如实推进；
  隐瞒变更只会制造更难查的静默覆盖，与 If-Match 的存在意义相悖。
- 前端打开页面后轮询版本号：落选。定时轮询增加无效请求，且与 412 触发时的
  按需刷新重复；重试一式已覆盖全部写入口，无需新增常驻机制。
- 保留原"并发写入拦截"文案只改标题：落选。用户困惑的核心正是文案把系统
  后台行为指控为"其他管理终端"，换汤不换药等于没修。

## Consequences

- 验证：vitest 68 项绿（含新增"瞬时 412 自动重试成功不弹窗"与原有
  "持续 412 仍弹窗"）；typecheck、lint、生产构建通过。
- 恢复条件：若未来出现重试也盖不住的高频后台写入（如轮换风暴），再考虑
  在后端为轮换写盘与人工写盘拆分版本域，而非放宽前端重试次数。
